# 其他運算服務：Beanstalk、Lightsail、Batch、Outposts

前面已經介紹過 EC2、容器、Fargate 和 Lambda。這一章再補充四個運算服務。

## 你想掌控多少，還是想省事多少

AWS 有很多運算服務，但它們其實都在回答同一個問題：**「伺服器的大小雜事，你想自己管多少？」**

可以用吃飯來比喻：

- 自己買菜、自己煮：最自由，想煮什麼都可以，但從洗菜到收拾都要自己來。這就像 **EC2**。
- 肚子餓了才叫外送，吃完就結束：完全不用管廚房，也不用準備食材。這就像 **Lambda**。

愈靠近「自己來」，你的掌控權愈大，要處理的雜事也愈多；愈靠近「別人幫我做」，就愈省事，但你能自己決定的部分也愈少。**沒有哪一種比較高級，只有哪一種比較適合你現在的情況。** 這一章介紹的四個服務，有些落在這兩端之間，有些則是用來處理其他特殊需求。

## Beanstalk 與 Lightsail

假設你已經寫好一個網站，只想讓它上線，不想花時間搞懂負載平衡器和自動擴展。AWS 有兩個服務，就是為這種情況設計的。

**Elastic Beanstalk**：如果直接用 EC2 架設一個可以正式上線的網頁應用，你得自己把 EC2、負載平衡、自動擴展這些元件一個一個設定好。用 Beanstalk，你**只要上傳程式碼，它就會自動建立這些底層元件**。之後如果需要，你還是可以自己調整底層設定，所以掌控權並沒有完全交出去；但在預設情況下，你什麼都不用碰。這種「你負責程式，平台負責基礎設施」的服務，業界稱為 PaaS。

**Lightsail** 更加簡單。它把一台虛擬伺服器和**固定、清楚的月費**包成一個方案，讓你不必研究 AWS 各種複雜的計價方式。Lightsail 適合簡單的網站、小型應用，也適合第一次使用 AWS、只想盡快把東西架起來的人。

> - 題目強調「上傳程式碼、自動部署」：選 **Beanstalk**
> - 題目強調「簡單、定價單純、入門」：選 **Lightsail**

## Batch 與 Outposts

AWS Batch 是給「一次要跑一大批運算工作」的情況用的。例如一個晚上要渲染幾千張影像，或執行大量科學運算。這時你不會想一台一台手動開機器、安排工作順序、再把機器關掉。Batch 會幫你管理和排程這些批次工作，需要多少運算資源就提供多少，工作完成後自動釋放資源。這些工作實際上執行在 EC2、Fargate 或 EKS 上；Batch 負責的是排程和管理。

**AWS Outposts** 處理的是**地點**問題，而不是省事問題。有些情況下，你**必須在自己的機房裡執行系統**，例如法規要求資料不能離開公司，或應用對延遲非常敏感；但你又想沿用 AWS 的操作方式和服務。Outposts 的做法是：AWS 把自己的硬體和服務**實際搬進你的機房**，讓你在地端也能用管理雲端的方式管理系統。

## 所有運算選項

```
掌控最多、要管最多 ◄──────────────────────────► 最省事、要管最少
   EC2  →  ECS/EKS on EC2  →  ECS/EKS on Fargate  →  Lambda
```

| 情況 | 選擇 |
|----------|--------|
| 要完全掌控作業系統、長時間執行 | EC2 |
| 已經容器化、自管底層主機 | ECS/EKS（跑在自管的 EC2 上）|
| 已經容器化、不想管底層主機 | ECS/EKS（跑在 Fargate 上）|
| 短小、事件觸發、不想管任何伺服器 | Lambda |
| 要把多個步驟 / 服務串成一個流程 | Step Functions |
| 有程式碼，想讓 AWS 自動處理部署 | Elastic Beanstalk |
| 簡單網站 / 小應用，要最簡單 | Lightsail |
| 一次要跑大量批次運算 | AWS Batch |
| 法規 / 延遲要求，必須在自己機房用 AWS | Outposts |

> 這張表不需要死背。只要先抓住「掌控 vs 省事」這個原則，大部分選項都能自己判斷出來。Batch（大量批次運算）和 Outposts（在地端使用 AWS）不在這個比較範圍內，要另外記。

## 重點整理

- **Elastic Beanstalk** = 上傳程式碼，AWS 自動建立底層環境（PaaS）；**Lightsail** = 簡單的小主機，定價清楚
- Beanstalk 容易和 Lightsail 混淆：記住「上傳程式碼」選 Beanstalk，「一台小主機」選 Lightsail
- **AWS Batch** = 大量批次運算
- **Outposts** = 在自己的機房裡使用 AWS
