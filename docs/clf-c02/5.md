# 容器：ECS、EKS、Fargate 與 ECR

容器（container）有什麼好處、它和 EC2 有什麼不同、怎麼把程式打包成映像檔、怎麼選擇編排器，以及底層主機要由誰管理。

## 為什麼要用容器：先看它和虛擬機的差別

要理解容器，最快的方法是拿它和第 2 章的 **EC2（虛擬機）** 比較。

一台虛擬機（VM）就像一整台電腦的數位複本。它有自己完整的作業系統，執行在 hypervisor（虛擬化層）上。所以每開一台 VM，就要多執行一套完整的作業系統：開機比較慢、比較佔空間，資源也要事先準備好。

**容器**則只打包「你的程式」和「程式需要的相依套件」，並**共用底層主機的作業系統核心**。因為不用每次都帶著一整套作業系統，容器輕量、啟動快、好搬移。

> 用貨櫃來想「容器（container）」這個名字：貨櫃把貨物用一個標準化的箱子裝好，不管換到哪艘船、哪台卡車都能直接搬、不必重新打包。容器對軟體做的是同一件事——把程式連同環境裝進一個標準單位，在你的筆電、在測試機、在雲上跑起來都一模一樣，解決「明明我電腦上可以跑」的問題。

| | 虛擬機（如 EC2） | 容器 |
|---|---|---|
| 打包什麼 | 一整套作業系統 + 應用 | 只有應用 + 相依套件 |
| 作業系統 | 每台各有一份完整 OS | 共用主機的 OS 核心 |
| 啟動速度 | 較慢（要開機） | 極快 |
| 資源佔用 | 較重 | 輕量 |
| 隔離強度 | 強（完整隔離） | 相對輕（行程層級隔離）† |

> † **Fargate 是例外**：每個 Fargate task 都有自己的隔離邊界，不和其他 task 共用核心。

## 映像檔與容器

- **映像檔（Image）** 是「範本」：一個唯讀的打包成品，裡面有程式和它需要的環境。可以把它想成餅乾模具。
- **容器（Container）** 是「用範本啟動的執行實體」：也就是從映像檔啟動、正在執行的程式。可以把它想成用模具壓出來的餅乾，一個模具可以壓出很多片。

流程是：先做出映像檔 → 存到倉庫 → 需要時從映像檔啟動一或多個容器。那個「倉庫」在 AWS 上就是稍後會講的 ECR。

```mermaid
architecture-beta
    group cloud(cloud)[AWS Cloud]

    service build(server)[Image Build]
    service ecr(aws:amazon-elastic-container-registry-registry)[ECR] in cloud
    service c1(aws:amazon-elastic-container-service-container-1)[Container] in cloud
    service c2(aws:amazon-elastic-container-service-container-1)[Container] in cloud

    build:R --> L:ecr
    ecr:R --> L:c2
    ecr:B --> T:c1

    align row build ecr c2
    align column ecr c1
```

*打包好的映像檔推送到 ECR 保存。需要時，同一個映像檔可以啟動一個或多個容器。*

## 編排（Orchestration）

只有一兩個容器時，你還能自己手動管理。但容器一多，到了幾十、幾百個，就會遇到一堆問題：每個容器該放在哪台機器上？某個容器當掉了，要不要自動重啟？流量變大時要不要多開幾個，流量變小時要不要關掉一些？工作要怎麼分給多台機器？

**自動幫你處理這些事的系統，就叫做編排器（Orchestrator）**，它是容器世界的「調度中心」。在 AWS 上跑容器，有兩個問題要分開決定。

### 決定一：用哪個編排器

| 編排器 | 是什麼 | 選它的理由 |
|---|---|---|
| **ECS（Elastic Container Service）** | AWS 原生的容器編排服務 | 較簡單、與 AWS 服務整合最好、控制平面免費 |
| **EKS（Elastic Kubernetes Service）** | AWS 託管的 Kubernetes | 開源業界標準、可跨雲 / 地端移植、團隊已熟 K8s |

**ECS** 是 AWS 自己設計的編排器。它的控制平面（control plane）負責決定容器怎麼調度，完全由 AWS 管理，你不必碰。所以 ECS 上手最快，和 IAM、ALB、CloudWatch 等 AWS 服務的整合也最好。缺點是 ECS 是 AWS 專屬的服務，只能在 AWS 上使用。

**EKS** 則是由 AWS 代管的 **Kubernetes**。Kubernetes 是業界最主流的開源容器編排標準，常簡寫成 K8s。選擇 EKS 最主要的理由是**可攜性和標準化**：同一套 Kubernetes 設定和工具，可以用在 AWS、其他雲端，甚至自家機房。缺點是 Kubernetes 本身比較複雜，要先學會它的術語和運作方式。

> **ECS vs EKS**
> - 想要 AWS 原生、簡單、整合好：選 **ECS**
> - 想要開源的 Kubernetes、能跨雲移植，或團隊已經在用 K8s：選 **EKS**

### 決定二：容器實際跑在哪

| 運算選項 | 誰管主機 | 你要負責什麼 |
|---|---|---|
| **EC2**（在 ECS 稱為 EC2 啟動類型） | 你自己 | 準備 EC2、修補更新、規劃容量與擴展 |
| **Fargate** | AWS（無伺服器） | 只管容器本身，主機完全不用碰 |

- **EC2**：容器執行在一群由你自己管理的 EC2 上。你的掌控權最大：可以挑選機型、安裝特殊軟體，用量穩定時也可能比較省錢。但這些主機的修補更新、容量規劃和擴展，都要你自己負責。
- **Fargate**：無伺服器模式。你只要告訴 AWS「我要執行這個容器，給它多少 CPU 和記憶體」，AWS 就會在背後準備好主機來執行。**你完全不用管任何伺服器**，費用依你為容器設定的 CPU 和記憶體，按使用時間計算。

> 📌 **要不要自己管主機**
> - 完全不想管主機、想最省事：選 **Fargate**
> - 想自己管理 EC2 主機、需要最大的掌控權：選 **EC2**

## ECR：存放映像檔的私有倉庫

**ECR（Elastic Container Registry）** 是 AWS 代管的私有映像檔倉庫。你把打包好的映像檔推送（push）上去，ECS 或 EKS 要執行容器時，再從這裡拉取（pull）下來。ECR 會**保存映像檔並管理版本**，也和 IAM 權限整合。它還能對映像檔做**弱點掃描**，檢查裡面的套件有沒有已知漏洞。

> 📌 ECR 是「存放映像檔的地方」，ECS / EKS 是「用映像檔執行容器的地方」。

## 完整架構

```
        ┌─ 編排器：ECS（AWS 原生） 或 EKS（Kubernetes）  ← 決定一
容器 ───┤
        ├─ 跑在哪：EC2（自管主機） 或 Fargate（免管主機）  ← 決定二
        │
        └─ 映像檔倉庫：ECR（ECS / EKS 從這裡拉映像）
```

把上面介紹的服務依序串起來，就是一個容器化應用從打包到上線的完整流程：

```
1. 打包    你的網站程式 → 做成 Docker 映像檔
2. 上傳    把映像檔 push 到 ECR（私有倉庫）
3. 定義    告訴 ECS：要跑哪個映像檔、給多少 CPU / 記憶體
4. 執行    ECS 在 Fargate 上啟動容器（主機 AWS 管，你不用碰）
5. 分流    前面掛一個 ALB，把使用者流量平均分到多個容器
6. 伸縮    流量大自動多開容器、流量小自動收掉
```

在這個流程裡，每個服務各有分工：**ECR** 存放映像檔，**ECS** 負責調度容器，**Fargate** 提供執行容器的主機，**ALB** 把流量分配給各個容器。

## 容器 vs Lambda vs EC2：什麼時候選容器

容器不是唯一的運算選擇。它的定位介於 EC2 和 Lambda 之間：

- 需要完全掌控作業系統，或要執行常駐、特殊的工作：選 EC2
- 工作短小、由事件觸發，而且希望閒置時不付錢：選 Lambda
- 想把應用打包成到哪裡都能一致執行的單位、建立微服務，或把現有的 Docker 應用搬上雲端：選容器（ECS / EKS）

## 重點整理

- **容器 vs 虛擬機**：容器只打包「應用 + 相依套件」、**共用主機的 OS 核心**，所以輕量、啟動快、容易搬移；VM（如 EC2）各自帶一份完整 OS，比較重，但隔離更強。兩者常搭配使用（容器跑在 VM 裡）。
- **映像檔 vs 容器**：映像檔是唯讀範本，容器是從映像檔啟動的執行實體；一個映像檔可以啟動多個容器。
- **編排（Orchestration）** = 自動調度大量容器（排程、重啟、擴縮）。
- **兩個要分開的決定**：①用哪個編排器：**ECS（AWS 原生、簡單、控制平面免費）vs EKS（開源 K8s、可跨雲、較複雜）**；②容器跑在哪：**EC2（自管主機、掌控權最大）vs Fargate（免管主機、最省事）**。
- **ECR** = 私有映像檔倉庫，ECS / EKS 從這裡拉取映像檔，支援版本管理與弱點掃描。

| 情境需求 | 答案 |
|---|---|
| 要 AWS 原生、最簡單的容器編排 | **ECS** |
| 要開源 Kubernetes、可跨雲 / 地端移植 | **EKS** |
| 跑容器但完全不想管底層主機 | **Fargate** |
| 跑容器且要自管 EC2 主機、要最多掌控 | **EC2（ECS 的 EC2 啟動類型）** |
| 存放與版本管理容器映像檔 | **ECR** |
| 掃描映像檔裡的已知漏洞 | **ECR（映像檔掃描）** |
| 把既有 Docker 應用一致地搬上雲 | **容器（ECS / EKS）** |
| 短小、事件觸發的工作 | **Lambda**|
