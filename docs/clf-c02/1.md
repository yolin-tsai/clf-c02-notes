# 雲端入門

Amazon Web Services（AWS）是全球最大的雲端平台，提供運算、儲存、資料庫、網路等數百種服務。這些服務需要時就能開啟，用完隨時可以關閉。
這章介紹雲端的定義、服務分層方式、實體基礎設施，以及安全責任的劃分。

## 什麼是雲端運算

用傳統做法，公司要架設一套系統，得先買伺服器、租機房、請人維護，而且這些費用在系統上線前就要付清。公司還得事先猜測：未來需要多大的容量？猜多了，多買的機器只能閒置，錢等於白花；猜少了，流量一大系統就會當機，這時再加買機器也來不及。

有了雲端，就不必再做這種猜測。**雲端運算是「透過網際網路按需取用 IT 資源，並依用量付費」**。這就像用電：電費按度數計算，你家不需要自己買發電機。

從財務角度來看，雲端最重要的優勢是：IT 支出從 **CapEx** 變成 **OpEx**。

| 名詞 | 意思 | 例子 |
|------|------|------|
| **CapEx**（Capital Expenditure，資本支出）| 事先一次付一大筆錢，買下設備 | 買伺服器、蓋機房 |
| **OpEx**（Operating Expenditure，營運支出）| 用多少付多少，費用隨用量變動 | 按月付 AWS 帳單 |

以學校選課系統為例：開學前兩天是選課高峰，幾萬人同時搶課；其餘 90% 的時間幾乎沒有流量。如果學校自建機房（CapEx），就得照尖峰時的需求一次買足伺服器，但這些伺服器平常大多閒置，電費卻照樣要付。換成雲端（OpEx），學校可以在選課期間自動增加伺服器（scale out），選課結束後再自動減少（scale in），只為實際用到的部分付費。

### 三種部署模型

公司的資訊系統和資料庫，都需要放在伺服器上才能運作。過去，公司會把伺服器放在自己的機房，自己採購、自己維護。這種做法稱為**地端（On-premises）**，也就是前面說的傳統做法。

後來出現了 AWS、Google Cloud（GCP）、Microsoft Azure 這些雲端平台。公司不必再自己買伺服器，可以改向雲端業者租用，用多少付多少。這種做法稱為**雲端（Cloud）**。

不過，很多公司沒辦法把所有系統都搬上雲端，只好兩邊混用，這稱為**混合（Hybrid）**。常見的原因有三個：

- 法規或公司規定要求某些資料必須留在自己的機房。
- 公司剛花大錢買了設備，還沒到該汰換的時候。
- 系統太多，沒辦法一次搬完，只能分批搬上雲端。

| 模型 | 說明 | 適合 |
|------|------|------|
| **雲端（Cloud）** | 全部跑在 AWS 等雲端平台 | 新創、雲端原生應用 |
| **地端（On-premises）** | 全部在自己機房，自行採購與維護實體硬體 | 法規嚴格、已在自有機房投入大量資金 |
| **混合（Hybrid）** | 部分在雲、部分在本地，兩邊連通 | 逐步上雲、特定資料須留在本地 |

### 三種服務模型

使用雲端時，你可以選擇自己要管理多少東西。從 IaaS、PaaS 到 SaaS，AWS 替你管理的部分愈來愈多，你能控制的細節也愈來愈少：

| 模型 | 你管什麼 | AWS 管什麼 |
|------|---------|-----------|
| **IaaS**（基礎設施即服務）| OS 以上全部（自己裝系統、設定環境）| 硬體、網路、虛擬化 |
| **PaaS**（平台即服務）| 只管程式碼與資料 | OS、執行環境 |
| **SaaS**（軟體即服務）| 直接用，幾乎什麼都不管 | 幾乎全部 |

可以用吃披薩來記這三種模型。IaaS 像租一間有烤箱的廚房，麵團和配料都要自己準備；PaaS 像店家已經備好麵皮和烤箱，你只要帶自己的配料（程式碼）；SaaS 像直接去餐廳點一份做好的披薩。從 IaaS 到 SaaS，你要管的事愈來愈少，能自己決定的事也愈來愈少。

延伸閱讀：[IaaS vs. PaaS vs. SaaS（Red Hat）](https://www.redhat.com/en/topics/cloud-computing/iaas-vs-paas-vs-saas) 


## 雲端的六大好處

AWS 歸納出使用雲端的六大好處：

| # | 英文 | 好處 | 情境 |
|---|---------|------|-----------|
| 1 | Trade Fixed Expense for Variable Expense | 不先砸錢買設備，用多少付多少 | 「不想先投入大筆資本」|
| 2 | Benefit from Massive Economies of Scale | 數百萬客戶集中採購，單位成本較低 | 「降低單位成本」|
| 3 | Stop Guessing Capacity | 要多少開多少，不用猜 | 「不確定流量」「避免猜錯容量」|
| 4 | Increase Speed and Agility | 幾分鐘部署，不用等採購 | 「快速實驗 / 上線」|
| 5 | Stop Spending on Data Centers | 不必管機房、電力、硬體 | 「專注本業，不想管基礎設施」|
| 6 | Go Global in Minutes | 幾個步驟就能在全球各地上線 | 「服務全球使用者 / 降低延遲」|

### 1. Trade Fixed Expense for Variable Expense（以變動支出取代固定支出）

「固定支出」是指：不管這筆投資將來划不划算，你都得在**第一天先付清一大筆錢**。如果是新產品，這樣做的風險特別高，因為產品還沒有任何使用者，也不知道會不會成功。猜對了，當初買的機器剛好夠用；猜錯了，結果只有兩種：買太多，機器整年閒置、不斷折舊；買太少，產品真的紅了，卻來不及擴充。

使用雲端後，這筆錢變成「變動支出」：費用依**實際用量**計算。一個乏人問津的專案的專案幾乎不花錢；使用者愈來愈多的專案，費用才跟著規模增加。也就是說，你只為實際用到的資源付費，不必事先投入大筆資金。這也讓嘗試新點子變得容易：想驗證一個點子，成本從一張伺服器採購單，變成幾個小時的運算費用。

### 2. Benefit from Massive Economies of Scale（享受規模經濟）

規模經濟的運作原理：數百萬個客戶都在 AWS 上使用資源，所以 AWS 採購硬體、電力和網路的數量，遠遠超過任何一家公司。買得愈多，每一單位的成本就愈低。又因為雲端按用量計價，業者之間也互相競爭，AWS 會把省下來的成本，以**更低的價格**回饋給每個客戶。

可以把 AWS 想成量販店：量販店一次替幾百萬人進貨，所以能談到很低的單價；一般家庭自己去買，永遠拿不到這種價格。

### 3. Stop Guessing Capacity（免除預估容量）

自建機房最難的地方是：你必須在**資訊最少的時候**（也就是上線前），就決定要買多少容量。猜錯的結果只有兩種。猜多了，一整排伺服器閒置，電費和折舊卻照算；猜少了，流量一大系統就當機，而加買實體伺服器要等好幾週，根本來不及。

使用雲端就不必再猜：需要多少資源就開多少，再搭配 **Auto Scaling**，讓資源隨實際需求自動增減。以前面的選課系統為例，選課那兩天伺服器自動增加，選課結束後自動減少，學校完全不必事先預測尖峰有多高。這種「隨需求彈性伸縮」的能力，是雲端最具代表性的優勢。

### 4. Increase Speed and Agility（提升速度與敏捷性）

過去要拿到一台伺服器，得經過採購、下單、等貨、上架安裝，前後往往要好幾週，甚至好幾個月。等這麼久還有一個不容易察覺的代價：既然「開一台機器」又慢又貴，團隊就**不敢輕易嘗試**有風險的新點子。

在 AWS 上建立一套環境只要幾分鐘，不用時也能隨時刪除，刪除後就不再計費。當「試一次」幾乎不花錢，團隊做事的方式就會改變：可以放手實驗，失敗了代價也不高，還能快速迭代。敏捷性的重點不只是「快」，更在於實驗成本低了，團隊才有放膽去試的自由。

### 5. Stop Spending Money on Running and Maintaining Data Centers（省下維運機房的費用）

自己經營一座資料中心需要持續花錢，是一筆和你真正的產品毫無關係的持續開銷：供電、散熱、實體門禁，定期更換故障硬體，還要有專人上架伺服器，半夜也可能得去換壞掉的硬碟。AWS 把這類工作稱為「undifferentiated heavy lifting（無差異化的粗重工作）」。意思是，這些工作做得再好，也不會讓你的產品更有競爭力。

把這些工作交給 AWS 之後，你的工程師就能專心開發應用程式本身，這才是讓產品與眾不同的地方。對一間新創來說，這代表工程師可以把時間花在寫新功能，而不是跑去機房換硬碟。

### 6. Go Global in Minutes（數分鐘內全球部署）

用傳統做法，如果要服務另一個大洲的使用者，你得在當地找地點、租機房，再把設備一步步建起來。這是好幾個月的工程，成本又龐大，以致多數公司根本做不到。

AWS 在全球各地都設有 Region。要把服務擴展到新的地區，只需要在當地的 Region 部署，使用者就能連到離自己最近的機房，延遲更低，使用起來也更穩定。原本「拓展到全球」是一項耗時又昂貴的工程，現在只要**幾個步驟**就能完成。舉例來說，台灣的應用程式想服務美國使用者，只要在美國的 Region 再部署一份，美國使用者就不必跨越整個太平洋連線。

## AWS 全球基礎設施

AWS 的實體設施分成三個層級。這樣分層不只是為了地理上的方便，更是為了隔離故障：

```
Region（區域，如 ap-northeast-1 東京）
  └─ Availability Zone（可用區，一個 Region 通常 ≥ 3 個）
       └─ 一或多個實體資料中心
（另外散布全球的）Edge Location（邊緣節點）→ 給 CloudFront 做快取
```

| 層級 | 是什麼 | 重點 |
|------|--------|------|
| **Region（區域）** | 全球各地的地理區域 | 彼此**獨立隔離**；資料預設不自動跨 Region 移動 |
| **Availability Zone（可用區，AZ）** | Region 內獨立的資料中心群 | 實體隔離（不同電力 / 機房），但以低延遲高速網路相連 |
| **Edge Location（邊緣節點）** | 散布全球的快取點，數量遠多於 Region | CloudFront 用它把內容放到離使用者最近的地方 |

為什麼一個 Region 要分成多個彼此隔離的 AZ？因為這樣一來，就算其中一個 AZ 失火或斷電，其他 AZ 仍能正常運作。所以把應用程式部署在多個 AZ，是高可用架構的基礎。

> 📌 **全域服務 vs 區域服務**：EC2、S3、RDS 等絕大多數服務都是**區域服務**，建立資源時要先選定一個 Region。少數服務是**全域服務**，不必選 Region，例如 **IAM**（帳號與權限）、**Route 53**（DNS）、**CloudFront**（CDN）、**帳單（Billing）**。

### 如何選擇 Region

選擇 Region 時，要綜合考量四個因素：

1. **法規與資料落地（Compliance）**：如果法規要求資料必須存放在某個國家，就只能選該國的 Region。這一項優先於其他三項。
2. **鄰近使用者（Proximity）**：選離使用者近的 Region，延遲比較低。
3. **服務可用性（Feature availability）**：新服務不一定每個 Region 都有，要先確認。
4. **定價（Pricing）**：同一項服務在不同 Region 的價格不同。

## 責任共擔模型（Shared Responsibility Model）

使用 AWS，不代表安全問題全都交給 AWS 處理。安全責任由 AWS 和你分工負責：

```
AWS  負責「雲本身的安全」（Security OF the Cloud）
你   負責「雲裡面的安全」（Security IN the Cloud）
```

| 誰負責 | 範圍 |
|--------|------|
| AWS | 實體資料中心、硬體、底層網路、虛擬化層 |
| 你 | 資料、IAM 權限設定、OS 與防火牆（EC2）、加密設定、應用程式 |

責任的界線會隨服務類型改變。服務的託管程度愈高，AWS 替你代管的部分就愈多，AWS 負責的範圍也就愈大。以「系統更新」為例：

- EC2（IaaS）：你擁有 OS 的 root 權限，所以 OS 更新要自己負責
- RDS（託管服務）：OS 和資料庫引擎的更新都由 AWS 負責，你只要管理資料與存取權限

> 📌 無論用哪種服務，**資料**與 **IAM 權限設定**永遠是客戶的責任。

## 重點整理

- **雲端運算** = 透過網路按需取用 IT 資源、依用量付費
- 部署模型：雲端 / 地端 / 混合
- 服務模型：**IaaS**（自管 OS，如 EC2）、**PaaS**（只管程式碼，如 Beanstalk）、**SaaS**（直接用，如 Gmail）；愈往 SaaS，AWS 管得愈多
- 六大好處：考題會給情境，要能對應到關鍵字；最重要的是**免除預估容量**（對應 Auto Scaling）
- 全球基礎設施三層：**Region**（獨立的地理區域）> **AZ**（實體隔離、以低延遲網路相連的機房群）> **Edge Location**（CloudFront 快取點，數量最多）
- 部署在多個 **AZ** = 高可用的基礎（一個 AZ 故障，其他 AZ 仍可運作）
- 選 Region 四考量：**法規與資料落地 > 鄰近使用者 > 服務可用性 > 定價**
- **全域服務**：**IAM、Route 53、CloudFront、帳單**；其他絕大多數服務都是區域服務
- **責任共擔**：AWS 管「雲本身的安全（OF）」，客戶管「雲裡面的安全（IN）」；OS 更新：EC2 由客戶負責，RDS 由 AWS 負責
- 資料與 IAM 權限設定永遠是客戶責任，與服務類型無關
